# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview
Speed Log is a client‑side log viewer for ArduPilot. It runs purely in the browser (no server) and is distributed as a static web page, a PWA, and an Android wrapper. All source files live in the repo root; there is no build system beyond the `node build.cjs` script that inlines the third‑party modules and emits `dist/SpeedLog.html` and the `site/` folder for deployment.

## Common commands
- **Setup / linting** – `npm ci` (Node ≥ 22.13).  `npm run lint` checks correctness via the custom `eslint.config.mjs`.  No tests are bundled.
- **Local development** – `python3 -m http.server --bind 127.0.0.1` and open `http://127.0.0.1:8000/`.  The server serves files as cache‑able; reload with `fetch(file,{cache:'reload'})` to see code changes immediately.
- **Single‑file build (web)** – `node build.cjs`.  Generates `dist/SpeedLog.html` (inlined JS/CSS) and the `site/` directory (PWA assets, `sw.js` with a build‑time hash).  `dist/SpeedLog.html` is the file bundled into the Android WebView.
- **Android debugging** – after running `node build.cjs`, from `android/` run `gradle assembleDebug` (Gradle 8.14).  The resulting APK (`app/debug/app‑debug.apk`) contains the built HTML.  For release builds use `gradle assembleRelease` and sign with the JKS in the user‑specific `keystore.properties`.
- **PWA** – the `index.html` contains a `<!-- pwa -->` marker that `build.cjs` replaces with the service‑worker registration.  The PWA can be installed from the browser; the `manifest.webmanifest` and `sw.js` are generated automatically.

## Architecture highlights
- **Global script style** – all logic lives in plain‑JS files that are loaded via `<script src>`; there is no module system.  Functions and state are attached to the `window` object or to modules that expose a global.  Refactoring to ES modules is discouraged unless a clear benefit exists.
- **Root layout** – key entry files:
  - `index.html`: bootstraps the app, loads scripts, contains PWA marker.
  - `SpeedLog.js`: core plotter, panels, tables, and the main `setup()` routine.
  - `chrome.js`: UI chrome – menus, side drawer, preferences, shortcuts, focus mode.
  - `views.js`: tab management, tool loading, status icons, PID form wiring.
  - `hardware.js` / `pid.js`: legacy tools now maintained here; ignore lint warnings as they are generated.
  - `i18n.js` / `i18n_tools.js`: translation tables; add new keys here.
  - `descriptions.js` & `markup.js`: generated data; regenerate via `node build.cjs`.
  - `board_types.js`: board‑ID lookup; loaded before `hardware.js`.
  - `libraries/`: helper utilities (e.g., `LogHelpers.js`, `fft.js`).
  - `modules/`: vendored third‑party libs (Plotly, FFT, floating‑UI, tippy, JsDataflashParser).  Replace a file only with a newer upstream build; do not edit them.
- **Data flow** – Log parsing is performed by `JsDataflashParser` in the browser.  The parsed data is fed into `SpeedLog.js` which creates the visualizations.
- **UI conventions** – screen mode classes (`html.mode-desktop|compact|phone|tablet`), `html.side-drawer` flag, CSS variables `--topbar-h` and `--chrome-h`.  Persistence is via `pref_get`/`pref_set` using keys prefixed with `logviewerlite-`.  Text elements use `data-i18n*` attributes; the rendering engine resolves them from the i18n tables.

## Development workflow
1. **Pull latest changes**.
2. **Run `npm ci`** to install lint dependencies.
3. **Make your changes** in the relevant JS files.  Avoid editing generated files directly.
4. **Run `npm run lint`** – all files must pass the linting rules before committing.
5. **Test locally** with `python3 -m http.server` or rebuild the Android package.
6. **Commit** only after lint passes and local tests confirm the change.

## Android build notes
- The Android wrapper (`android/`) uses a minimal WebView that loads `dist/SpeedLog.html`.
- Signing credentials are stored in a user‑specific `keystore.properties`; never commit it.
- To produce a release build: run `node build.cjs`, then `gradle assembleRelease` and sign with the existing JKS.  Update `versionCode` in `android/app/build.gradle` for each release.

## Known constraints
- No automated test suite; manual testing is required.
- Generated files (`descriptions.js`, `markup.js`) should not be edited manually.
- The code relies on global namespace; refactoring to modules must preserve the existing globals.
- The repository does not use a bundler; all assets are served statically.
